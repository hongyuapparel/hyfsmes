# Agent 协作规范

> 涉及执行边界、页面变更流程、验证回复、优先级、设置页即时生效时读取本文档。

---

## 1. 执行边界

- 只修改用户明确要求的页面、模块、文件或问题范围，不顺手扩散。
- 必须改动未点名内容时，先说明原因、范围、影响。用户已授权的必要根因修复可以继续；扩大功能范围、改变业务含义或不可逆操作且未获授权时才暂停确认。
- 改数据库结构、接口契约、全局样式或公共基础组件前检查影响范围和已有授权，不因“公共”二字重复索要已给出的确认。
- 不覆盖、不回退、不清理用户已有改动，除非用户明确要求。
- 发现代码、文档、规则冲突时，先说明冲突点，再继续。

---

## 2. 页面与业务变更

- 用户只描述业务需求且方案不清时，先明确目标、角色、核心操作和信息优先级，给 1 到 3 个方案；用户确认后再大面积实现。
- 设置类页面新增、编辑、删除后，当前界面必须立即可见结果，禁止依赖 F5、`location.reload`、`router.go(0)` 或外层动态 `key` 重建。
- 需求级变更完成后轻量同步文档，例如新增模块、调整关键流程、修改订单状态、统一字段配置、重构核心页面；小 bug 和小样式可不更新文档。
- 需求级变更在 `docs/PROJECT_CONTEXT.md` 追加一句决策记录；样式微调或小 bug 修复可不更新文档。
- 历史遗留问题不要加重；触碰相关区域时优先偿还，不能继续复制历史问题。

### 先核对事实，避免增加工作量

- 先查现有页面、字段来源和实际业务链路，再解释原因或设计方案。区分已确认事实、推测和待决定事项，不能把用户报错直接归因为操作不当。
- 同一名称可能指不同业务事件：购买、到料、交接、完成不可自行等同；客户交期与内部时限不可混用。修改判定前用真实例子核对口径。
- 自动带入已有资料，保留必要的人工修正；不能为实现方便要求重复录入、重复确认或把同一件事拆成多次操作。是否必填按业务要求确定，不擅自增加门槛。
- 订单计划、参考用量、实际用量和实际库存必须区分来源。缺失事实就明确缺失，不用比例、旧订单或猜测补成真实记录。
- 历史方案只作参考，新的明确纠正优先。不要把尚在讨论的业务方案固化为项目规则。

### 设置页即时生效（通用）

适用于所有设置/配置项页面（工序、供应商、仓库、类型、权限等）：

- 新增/编辑/删除后，当前界面必须立即可见结果，禁止依赖 F5 或手动刷新。
- 禁止用整页刷新或整块重建掩盖状态同步问题。
- 优先局部更新当前列表/树/表单状态；必须重拉时要恢复用户现场（筛选、分页、展开态、滚动位置）。
- 生产工序树专项：见 `.cursor/rules/30-order-settings-process-tree.mdc`。

## 3. 验证与回复

### 页面修改的默认验收要求

以下是默认工作要求，不需要用户每次补充提示词。验证范围覆盖本次改动及直接受影响的使用流程，不要求无关模块重复全测。

- 修改前列出本次可能影响的操作和验收点；交付前用最终版本实际操作，不能以构建通过、接口成功或页面文字存在代替用户可用。
- 改到抽屉、弹窗、表格或表单，必须用正常内容和长内容，检查常用窗口及较矮/较窄窗口。实际滚动到最后一项，确认底部记录和按钮可见、可操作，没有遮挡或截断；编辑、增加行和校验提示出现后重新检查。
- 改到业务操作，按真实角色走完直接受影响的流程，包括适用的填写、校验失败、取消、保存、重新打开核对、再次修改和操作记录。涉及权限或上下游资料时，验证对应角色能获得正确结果。纯样式修改不强制写业务数据。
- 图片必须区分真实图片、加载中、失败占位和无图；占位图显示不能算真实图片显示通过。测试数据必须覆盖问题场景；不足时使用隔离测试数据，不修改生产订单来凑测试。
- 对本次暴露的问题保留合适的回归检查；布局和滚动必须有浏览器实际操作证据，不能用只检查 CSS 字符串或 DOM 存在的测试代替。无需为简单样式堆砌无效测试。
- 回复简要列出实际验证的场景、结果和未验证项，区分本地预览与生产上线。没有验证到的内容不得写成“全部通过”或“可上线”；遇到登录、环境或数据阻碍，明确说明缺口并继续完成不受影响的检查。

### 验证结果与执行约束

- bug 反馈证据不足时不猜结论，先自行收集已授权可访问的页面、请求、复现步骤和日志；真正缺少访问或业务信息时再向用户索取。
- 修复后必须说明验证了什么、结果是什么；不能验证时明确告诉用户还需如何验证。
- 不能确认修复时明确说缺少哪项验证，继续完成可做的检查；不把开发者应做的测试转交用户，不声称“已修复完成”。
- 同一问题修复超过 2 次仍未解决时，停止猜测，列出已排除方向和仍需的新证据。
- sub-agent 返回「完成」不等于真完成；本人必须跑 build + 看 git diff 验证再向用户回报。
- 完成较大修改后简要说明：改了什么、关键文件、是否同步文档、验证结果、风险点。
- 本地启动或重启前后端时，默认使用 `scripts/start.ps1` 或 `scripts/restart.ps1` 隐藏窗口启动；不要主动打开可见命令窗口。需要排查时看 `logs/backend-3000.log`、`logs/frontend-5173.log` 或运行 `scripts/check.ps1`。

### 按改动触发的回归检查

只执行本次涉及的行，检查失败后继续定位；不是每次无差别测试整站。

| 改动涉及 | 必须验证的结果 |
|---|---|
| 输入、编辑、取消 | 输入后失焦、清空、填 0、保存后重新打开；取消后重新打开不保留误改。表格复制粘贴覆盖单格、选区和已有撤销行为，不能只调用保存接口。 |
| 数量、颜色、尺码 | 可见明细与合计、提交数据、再次读取、相关导出一致；改名、删列、清零不能留下隐藏数量。覆盖手填和来源选择、单色和多色、本次数量与累计数量。 |
| 筛选、排序、统计、导出 | 查询范围与列表、页签计数、合计和导出一致；覆盖父子选项、无结果、清空、分页。排序作用于全部查询结果，不能只排当前页。 |
| 状态、复制、补资料 | 复制新单不继承旧单完成记录；补资料不意外重走已完成流程。覆盖进行中与已完成订单，核对直接受影响的上下游页面。 |
| 完成、批量操作、权限 | 单选、多选、无选择及混合有效/无效数据；缺必填项不能绕过完成校验。前后端权限一致，批量失败要明确哪些未处理，不能笼统报成功。 |
| 操作记录、人员关联 | 记录对应真实动作、来源、操作者和时间；修改前后可追溯。人员改名后历史数据仍能关联、筛选，展示使用现有显示名规则。 |
| 公共控件、缓存页面 | 原报错页及同一组件的其他直接使用场景；首次打开、关闭重开、切换页签再返回、多实例共存。不能只在新开的单页验证。 |
| 打印、下载、模板 | 实际打开生成物或打印预览，核对页数、裁切、对齐、数量和约定模板内容；网页正常不代表打印正常。保持既有文件位置和样品/大货等输出约定，不擅改未要求的箱贴或模板。 |
| 性能、图片加载 | 在目标环境区分页面请求、接口/数据库、图片和渲染耗时；相同条件多次对比首次与再次打开，记录样本和限制。不能把本地快、单次快、占位图出现当作线上速度和真实图片通过。 |
| 修复历史数据 | 分清代码修复能否自动影响旧数据；需要补录或 SQL 时说明范围、执行前核对及执行后结果，不能把修代码说成历史数据已修好。 |

### 环境、同步与交付

- 测试前核对当前工作树/提交、前后端地址、进程和数据库目标；不要凭默认端口认定正在测试新版本，也不要输出密码等敏感配置。
- 用户要求先同步本地主分支时，先检查双方提交和未提交内容，合并后验证最终组合；只提交本任务文件，保留其他任务改动。禁止用清空工作区或覆盖文件的方式解决未知冲突。
- 已授权的合并、推送应执行到底，不能只给用户一条 `git push`。完成后核对本地主分支与远端提交；推送成功不等于生产发布成功。
- 部署使用当前 [`DEPLOY_GUIDE.md`](DEPLOY_GUIDE.md) 和实际脚本，核对目录、分支、服务名、端口及前后端范围；给可直接复制的命令。生产验收必须核对实际资源/服务版本及问题操作，不能只凭脚本退出成功。
- 项目规则应提交到主分支供新工作树继承，不能只写在个人记忆或某个工作树。已有工作树需合并新规则；从旧提交创建的工作树不会自动包含新规则。更新规则时同步入口指针、去除冲突，不复制多套正文。

历史案例与规则对应见 [`AGENT_LESSONS.md`](AGENT_LESSONS.md)。新的同类错误优先补充现有规则的验收条件，不无限追加重复条款。

---

## 4. 优先级

1. 用户当前明确要求。
2. 用户当前指定的文档或设计说明。
3. `AGENTS.md` 及本文档引用的 `docs/*` 规范。
4. 项目当前代码中的既有实现模式。

低优先级规则与高优先级规则冲突时，按高优先级执行，并在必要时说明。
